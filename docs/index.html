3080lab: measuring one GPU below CUDA

Luke Blommesteyn · November 2026 · code · lab notebook

NVIDIA publishes CUDA and PTX, but not the machine code its GPUs actually run (SASS), not how long each instruction takes, and not which hazards the hardware handles for you. I wanted to know how far you can get by measuring those things yourself on one card, an RTX 3080 in my desktop, and then using the measurements to write faster code than the compiler.

This is a summary of what came out of it. Short version: the measurements were good enough to beat ptxas on one specific problem (loads that split a 32-byte memory sector), to run Qwen2.5-1.5B 1.33× faster than llama.cpp on the same weights, and to pick GEMM tile sizes without searching. They were not good enough to beat the compiler's instruction scheduling in general, and in small search spaces they were no better than a rule of thumb plus a couple of measurements. Both halves are below.

No CUDA toolkit is installed for any of this. NVRTC, ptxas, nvdisasm and the driver API all come from pip wheels, and kernels are loaded as cubins, which is also how edited SASS gets run.

1. Measuring the machine

Every experiment is a small kernel whose timed loop is checked in the disassembly before it is allowed to run: if the loop doesn't contain exactly the expected instructions, or anything spills, the runner refuses. Trials are shuffled and interleaved between variants, and time comes from clock64() inside the kernel. Some of the resulting numbers:

The control bits

Each SASS instruction is 128 bits, and 21 of them (bits 105 to 125) are scheduling information the compiler leaves for the hardware:

fieldbitsmeaning
stall4cycles to wait before issuing the next instruction
yield1hint to switch warps
write barrier3scoreboard set when a variable-latency result (e.g. a load) is ready
read barrier3scoreboard set when the sources have been read
wait mask6scoreboards that must clear before this instruction issues
reuse4keep an operand in the operand reuse cache

I expected the hardware to interlock if the stall count was too small. It doesn't. Patching the stall on a chain of dependent FFMAs below 4 cycles produced wrong results in 20 of 20 trials. For fixed-latency instructions the stall field is the only protection, which means anything that rewrites SASS has to regenerate these bits exactly.

Register banks

The register file has two banks with one read port each. A three-operand FFMA whose sources are all in one bank can issue at most once every few cycles unless the reuse cache covers it:

Renumbering registers alone, with the same instructions in the same order, made a 50/50 FFMA:SHF mix 1.48× faster than ptxas's allocation.

2. Rewriting SASS

Memory is fetched in 32-byte sectors. In several int4 GEMV kernels, ptxas issues two loads that each need half of the same sector far apart in time, so the sector comes from memory twice. 3080lab optimize finds these pairs by analysing load addresses in the SASS, moves the second load next to the first, regenerates the control bits, checks for hazards, and compares the output bit for bit with the original.

To see whether this generalises, the tool was frozen and run blind on 120 int4 GEMV kernels. Suite A was used during development; B and C were not.

suitekernelsgeomean speedupwrong outputs
A (development)561.036×0

A general list scheduler built on the same hazard rules only reached parity with ptxas (1.003× on random kernels). An oracle picking the best of three orderings per kernel reaches 1.005×, so there was little left to find. Joint register allocation and scheduling, and software pipelining, also gave nothing measurable. My reading is that ptxas orders instructions well, and the opportunities are in things it doesn't model, like sector splitting.1

3. Qwen2.5-1.5B against llama.cpp

The engine loads llama.cpp's own Q4_0 GGUF of Qwen2.5-1.5B, repacking the weights bit-exactly, and runs decode as one CUDA graph of about 200 fused kernels. Batched decode uses tensor-core GEMVs and prefill uses int8 MMA directly on the Q4_0 nibbles. Both engines were run on the same card in six paired rounds with rotated order, plus an A/A arm, which agreed within 0.2%.

At batch 1 a token takes 1.95 ms, 63% of peak bandwidth for 928 MB of weights; most of the gain there comes from fewer, fused launches. Outputs match a token-by-token reference, and perplexity is within 0.1% of an fp16 path.2

4. Does the model help choose optimizations?

With a runtime model in hand, the next question was whether it can decide which optimization to apply. The split, predictors and metrics were committed before anything was fitted, and 771 decisions were measured.

For launch structure the model is within 0.2% of the oracle. For reordering, the oracle itself only gets 0.5%, which is below run-to-run noise, so there is nothing to predict.

5. Hardware model or autotuning?

If you can time every candidate and keep the fastest, a model is only useful if it gets there with fewer measurements. I tested that in several spaces, each with its decision rule committed before the numbers. In small spaces (4 to 21 candidates: GEMV layouts, fusion variants, an 18-tile GEMM set) the model did no better than a simple heuristic plus one or two measurements.

The larger case was the int8 prefill GEMM, which has 212 valid tile configurations. On Llama-3-8B's four linear layers at a 512-token prompt, shapes the cost model was never fitted on, every tile was timed and its output checked against an fp32 reference:

Four shapes is a small sample, so a larger, pre-registered benchmark is running now: 32 unseen workloads (Qwen2.5-7B, Gemma-2-9B, Phi-3-mini, Qwen2.5-14B at two prompt lengths), all 212 tiles each, comparing the model against random search and Optuna's TPE at budgets from 0 to 64 measurements. The question it answers is whether the model reaches within 5% of the best tile with at least 4× fewer measurements than TPE. The result will be added here either way.

What didn't work

  • A general SASS scheduler: parity with ptxas, never better.
  • Joint register allocation and scheduling, and software pipelining: no measurable gain.
  • Using the cost model to decide when to apply the sector rewrite: no better than always applying it, and 5 of 9 correct decisions under high register pressure.
  • Ranking close GEMM tiles: in earlier blind tests pairwise accuracy was 0.57. The model gets single-variable trends right (occupancy 15 of 16, k-chunk 29 of 30) but not launch bounds or ring depth.
  • One correctness check of mine compared NaN outputs, because the test activations weren't validly quantized, so it couldn't fail. It was replaced with a check that runs inputs through the production quantizer.

Method notes

Every comparison here uses interleaved, shuffled runs and an A/A control (two identical binaries timed against each other) to estimate the noise floor. Held-out tests have their split, metric and decision rule committed before the first number, and any later change is written up as a dated addendum. Everything was measured on one RTX 3080, and none of the hardware rules have been checked on another GPU. SASS rewrites are checked by a static hazard verifier and bitwise differential tests, not proven equivalent; the verification notes list the gaps.
