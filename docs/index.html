What one graphics card taught me

I spent a few months measuring a single RTX 3080 below CUDA, below PTX, down to the bits the compiler hides. Then I used what I found to rewrite its machine code and run a language model faster than llama.cpp. This is the whole story: the wins, the parts that only tied, and the ideas that didn't work.

0Why do this at all?

GPU programming has a strange layer cake. You write CUDA, NVIDIA's compiler turns it into PTX, and then a closed-source assembler called ptxas turns that into SASS, the real machine code. NVIDIA doesn't document SASS. It doesn't publish how long instructions take, which hazards the hardware catches for you, or how the register file is wired.

So the question I started with was simple: can one person measure the machine well enough to predict how fast code runs, and then write faster code than the compiler? One card, sitting in my desktop, one question at a time.

The short answer turned out to be "sometimes, and it's very specific about when." The rest of this page is the long answer.

No CUDA toolkit. Everything here runs on pip wheels: NVRTC to compile, ptxas and nvdisasm to assemble and disassemble, and the driver API to load raw cubins. That last part matters: if you can load a cubin, you can load one you edited by hand.

1Measuring the machine

Every instruction in SASS is 128 bits. Most of those bits say what to compute. But 21 of them, bits 105 to 125, are a little note from the compiler to the hardware about when. I decoded them by patching cubins and watching what broke. Tap a field:

control word, bits [105:125]

The stall field is where I got my first real surprise. I assumed the hardware would protect me if the compiler's number was too small, the way a CPU's pipeline interlocks do. So I took a chain of dependent multiply-adds and patched the stall below 4 cycles.

It gave wrong answers in 20 out of 20 trials. The hardware doesn't check. For fixed-latency instructions, those four bits are the only thing standing between your program and garbage. It's a lot of trust to put in a compiler, and it means anyone rewriting SASS has to get the timing exactly right.

The register file has two doors

A multiply-add reads three registers. The register file turned out to have 2 banks with one read port each, so if all three operands live in the same bank, the instruction has to wait. There's a small reuse cache to help, and the compiler sets those reuse bits, but it doesn't always get it right.

Just renumbering registers, with no change to the math, made one instruction mix 1.48× faster than what ptxas produced. That was the moment this stopped being a hobby and became a lab.

2Rewriting the compiler's homework

With the rules in hand, I wrote a tool that opens a compiled kernel, reads every load's address symbolically, and finds pairs that split a sector between them. Then it moves the late half up next to its partner, fixes every control bit, re-checks every hazard, and runs the result bit-for-bit against the original.

One kernel is an anecdote, so I froze the tool and ran it blind on 120 int4 GEMV kernels, most of which it had never seen:

suitekernelsgeomean speedupwrong answers
A (used while building)561.036×0
B (never seen)431.074×0

I also wrote a general instruction scheduler, hoping to beat ptxas everywhere. It reached parity, 1.003×, and no further. An oracle that picks the best of three orderings for each kernel only reaches 1.005×. The compiler is very good at ordering instructions. Where it leaves speed on the table is in places it doesn't model, like sector splitting.

3A whole language model

Microbenchmarks are fun, but I wanted to know if any of this adds up to something real. So I took Qwen2.5-1.5B, loaded llama.cpp's own Q4_0 weight file byte for byte, and wrote an engine around it: about 200 fused kernels captured in one CUDA graph, int4 GEMVs, tensor-core batched GEMVs, int8 tensor-core prefill and flash attention.

Then I raced it against the newest llama.cpp (b12428) on the same card, in paired, rotated rounds with an A/A control.

At batch size 1, a token takes 1.95 ms, which is 63% of the card's peak memory bandwidth spent reading 928 MB of weights. The win there is mostly about launching fewer, fatter kernels. The bigger wins at batch 8 come from reading each weight once and using it for every sequence on tensor cores.

Same bytes, same answers. Every tensor comes from llama.cpp's file. The last-token argmax matches a token-by-token reference, and perplexity is within 0.1% of an fp16 path. The two engines write the same coherent answers for the first eight words, then drift apart, because llama.cpp also quantizes activations.

4Can the model choose?

By now I had a hardware model that could predict a kernel's runtime with single-digit median error. The natural next question: can it decide which optimization to apply? I froze the split, the predictors and the metrics before fitting anything, then measured 771 decisions.

launch structure (fusion, CUDA graphs)1.159×1.229×1.231×
reordering SASS instructions1.000×1.0007×1.005×

For launch structure, the model lands within 0.2% of perfect. For instruction reordering, there's almost nothing to win, so even a perfect predictor barely helps. That was a useful thing to learn: most of the value is in deciding what the program looks like, not in shuffling its instructions.

5Model vs. autotuning

This is the question I care most about. If you can just try every option and keep the fastest (that's autotuning), why bother modelling hardware at all?

I tested it in five different search spaces, writing each rule down before seeing any number. In the small ones, with 4 to 21 candidates, the model added nothing: a simple rule of thumb plus a couple of measurements got just as close.

The big one was different. A GEMM kernel has 212 valid tile shapes. On four layer shapes from a model the cost model had never seen (Llama-3-8B), I timed every tile, checked every output against a reference, and asked: how close does each strategy get with a given number of measurements?

With zero measurements, the model's first guess is within 1.3% of the best tile. Sixteen random measurements still leave you 7% off. The production default tile is 22.6% off. So the honest answer is: hardware knowledge pays when the space is too big to search.

The proper test: 32 unseen workloads vs. a real autotuner

Four shapes isn't enough to believe in. A frozen benchmark is on the GPU as I write this: 32 workloads from Qwen2.5-7B, Gemma-2-9B, Phi-3-mini and Qwen2.5-14B, all 212 tiles each (6,784 pairs, every one checked against an fp32 reference), and the model racing Optuna's TPE autotuner at budgets from 0 to 64. The bar it has to clear, written down in advance: reach within 5% of the best tile with 4× fewer measurements than TPE. Whatever it says, it goes here.

6Things that didn't work

This list is longer than the list of wins, and I think it's the most useful part of the project.

  • A general SASS scheduler. Parity with ptxas (1.003×), never a win. The oracle ceiling is 0.5%.
  • Joint register allocation + scheduling, and software pipelining. No measurable gain.
  • Letting the model decide when to rewrite. "Guided" mode was no better than rewriting blindly, and fell to 5 of 9 correct calls under register pressure.
  • Hardware models in small search spaces. Tied a rule of thumb plus two measurements every time.
  • Ranking close GEMM tiles. Earlier blind tests: pairwise accuracy 0.57 for the better model. The model knows which direction occupancy goes; it does not know which of two good tiles is better.
  • The time I trusted a correctness check that couldn't fail. My test inputs made the reference output NaN, so every comparison "failed" and none of it meant anything. Caught it, rebuilt the check with properly quantized activations, then all 212 tiles passed.

7How I tried not to fool myself

A GPU is a noisy instrument, and it's very easy to see a 2% win that isn't there. A few rules I ended up living by:

  1. Measure noise first. Time two byte-identical binaries against each other (an A/A test). Anything smaller than that gap isn't a result.
  2. Interleave and shuffle. Never run all of A then all of B. Rotate the order every round so heat and clocks hit everyone equally.
  3. Write the rule down first. Before any held-out number exists, commit the split, the metric and what counts as a win. Amend only before the next number, and say so.
  4. Check outputs, not just times. A fast kernel that computes the wrong thing is the easiest win to fall for.
  5. Validate SASS before spending GPU time. The runner refuses to measure unless the timed loop has exactly the instructions it expects and nothing spills.
  6. Keep the negative results. They're in the notebook next to the wins, in the order they happened.

One GPU, one architecture: every rule here was measured on this RTX 3080, and none has been checked on another card. SASS rewrites are checked statically and differentially, not proven equivalent.
