Six weeks inside one graphics card

I spent six weeks poking at an RTX 3080 below CUDA, figured out a bunch of stuff NVIDIA doesn't document, and used it to run an LLM faster than llama.cpp. Some of it worked, a lot of it didn't.

Luke Blommesteyn · Oct 7 to Nov 16, 2026 · code · lab notebook
Prologue

Why one GPU

Some context: I used to have a 3090 with 24 GB of VRAM. I sold it (lowkey a dumb idea) and was left with a 3080 and 10 GB. So this started as me trying to get every last bit out of the card I still had.

When you write CUDA there are two compilers between you and the hardware. The second one, ptxas, is closed source, and the machine code it spits out (SASS) isn't documented. NVIDIA also doesn't tell you how long instructions take or what happens when one depends on another. So a lot of GPU perf advice is educated guessing.

I wanted to see how much of that I could just measure. Rules: one card, no CUDA toolkit (the compilers and disassembler all come from pip), and no claim without a measurement behind it.

I also did a lot of this with Claude (Opus 5.5). It wrote probe kernels and scripts, read disassembly with me, and pushed back when a result looked too good. Honestly it's the reason this took six weeks and not six months.

Part I

Measuring the machine

Turns out the hardware just trusts the compiler.

Every SASS instruction is 128 bits. Most of that is what to compute. Bits 105 to 125 are the compiler telling the hardware how long to wait and what to wait for. I figured out the fields by editing them in compiled binaries and seeing what broke.

I figured if the stall count was too low the hardware would catch it and wait anyway, like a CPU does. So I took a chain of adds where each one needs the last result and set the stall below 4 cycles.

Wrong answer 20 times out of 20. Exactly half the adds just vanished, because each one read the register before the previous write landed. There's no safety net. Those 4 bits are the only thing keeping your math right. Also weird: a stall of 0 doesn't mean "don't wait". It's correct but costs about 33 cycles, which is why -O0 code is so slow.

How long everything takes

After that it was a lot of measuring. The runner checks the disassembly of every timed loop before it runs, so I'm not accidentally timing something the compiler rewrote. Memory latency, for example:

A ceiling that turned out to be the compiler's fault

Ampere is supposed to run float and integer math at the same time. My float + integer mix never came close, and for a while I thought the hardware just couldn't. It was the register file. There are two banks, each does one read per cycle, and an FMA reads three registers. ptxas had put them in the same bank.

Part II

Beating the compiler, once

ptxas is usually right. I found one thing it isn't.

Memory comes in 32-byte sectors. In some quantized matrix-vector kernels, ptxas puts two loads that each need half of the same sector way apart, so by the second load the sector's gone and gets fetched again. So I wrote 3080lab optimize: it finds those pairs in the SASS, moves the second load up next to the first, redoes all the control bits, checks for hazards, and makes sure the output is bit-identical.

One kernel doesn't mean much, so I froze the tool and ran it on 120 kernels it had never seen:

Then I tried writing a whole instruction scheduler to beat ptxas everywhere. It tied, 1.003×, and never got better. Even picking the best of three orderings for every kernel only gets 1.005×, so there just isn't much there. It did catch a rule I'd missed (memory instructions need 4 cycles between them), which had been silently breaking one test suite.

Part III

A real model, end to end

Does any of this actually make tok/s go up?

I took Qwen2.5-1.5B and loaded llama.cpp's own Q4_0 file, so both engines read the exact same bytes, and wrote an engine around it: about 200 fused kernels in one CUDA graph, int4 kernels for single-stream decode, tensor cores for batches, int8 tensor cores for prefill. It was already 1.28× llama.cpp on day one. Here's where it is now against the newest llama.cpp:

Single stream is 514 tok/s. A token takes 1.95 ms, most of which is reading 928 MB of weights, and most of the win over llama.cpp is just launching fewer, bigger kernels. With more sequences the win gets bigger because each weight gets read once for all of them. Outputs match a token-by-token reference and perplexity is within 0.1% of fp16, so it's not fast because it's wrong.

Part IV

Model, or just search?

If you can just try everything, why bother modelling the hardware?

By November I had a model that predicts kernel runtime pretty well, and I wanted to know if it's actually useful for making decisions. I wrote down the test and what counts as a win before fitting anything, then measured 771 decisions:

decisionbest fixed rulemodeloracle
launch structure (fusion, CUDA graphs)1.159×1.229×1.231×
reordering SASS instructions1.000×1.0007×1.005×

For how to launch work, the model is basically perfect (within 0.2%). For reordering instructions there's only 0.5% to win in the first place, so it doesn't matter.

Against autotuning

Autotuning is just timing options and keeping the fastest. When there are only 4 to 21 options, the model didn't beat a rule of thumb plus a couple of tries. The prefill GEMM is different: it has 212 tile shapes. On four Llama-3-8B layers (which the model had never seen) I timed every single one:

The bar I set before running it: get within 5% of the best tile with 4× fewer measurements than TPE. Whatever it says goes here.
Part V

What didn't work

Longer list than the wins, ngl.

  • A general SASS scheduler. Parity with ptxas, never better. Joint register allocation plus scheduling, and software pipelining, didn't help either.
  • Letting the model decide when to rewrite. No better than always rewriting, and only 5 of 9 right calls under register pressure.
  • The decode megakernel. Wrong token, slower than the graph.
  • Ranking close GEMM tiles. In blind tests the model got single trends right (occupancy 15 of 16), but picking between two good tiles was close to a coin flip (0.57).
  • A correctness check that couldn't fail. My test inputs weren't quantized properly, so every output was NaN and the check was meaningless. Fixed it, reran it, everything passed.
  • Selling the 3090. tbh this was really dumb even though I got a lot of money for it.
Epilogue

How I tried not to lie to myself

GPU timings are noisy and it's really easy to see a 2% win that isn't real. Stuff I ended up always doing:

Time two identical binaries against each other first, and anything smaller than that gap doesn't count. Alternate A and B instead of running all of A then all of B, because the card heats up. Commit the rules for a test before running it, so I can't move the goalposts later. And check the outputs too, since a fast kernel that gives the wrong answer is useless.

All of this is one 3080. I haven't checked any of it on another card, and the SASS rewrites are tested, not proven correct (the verification notes list the gaps). The code, the raw data and the day-by-day notebook are all on GitHub.
