Six weeks inside one graphics card

I measured an RTX 3080 below CUDA, down to the bits the compiler doesn't document, then used what I found to rewrite its machine code and run a language model faster than llama.cpp. Here's how it went, including the parts that didn't.

Luke Blommesteyn · Oct 7 to Nov 16, 2026 · code · lab notebook
Prologue

Why one GPU

First, how I ended up with a 3080: I'd sold my 3090 not long before starting this. In hindsight, for a project that's entirely about squeezing one GPU, that was lowkey a dumb idea. So the 3080 it was.

When you write CUDA, two compilers stand between you and the hardware. The second one, ptxas, is closed source, and the machine code it produces (SASS) isn't documented. Neither is how long each instruction takes, or what the hardware does when two instructions depend on each other. Most GPU performance advice is built on top of that gap.

I wanted to see how much of it one person could fill in by measuring. The rules I gave myself: one card, no CUDA toolkit install (compilers and disassembler come from pip wheels), and every claim backed by a measurement I'd be comfortable showing someone.

I didn't do the reverse engineering alone. I worked with Claude (Opus 5.5) throughout: designing probe kernels, reading disassembly, writing analysis and benchmark scripts, and arguing about whether a result was real. Being able to try an idea in an afternoon instead of a week is most of why this fit in six weeks.

Part I

Measuring the machine

The first surprise was how much the hardware trusts the compiler.

Every SASS instruction is 128 bits. Most of it says what to compute. Bits 105 to 125 are different: a small note from the compiler telling the hardware how long to wait and which results to wait for. I worked out the fields by patching them in compiled binaries and watching what changed.

I assumed that if the stall count was too small the hardware would notice and wait anyway, the way a CPU pipeline does. So I took a chain of dependent adds, where each needs the previous result, and lowered the stall below its 4-cycle latency.

Wrong answers, 20 trials out of 20. Exactly half the increments disappeared, because each instruction read its register before the previous write landed. There's no safety net for fixed-latency instructions: those 4 bits are the only thing keeping the result correct. One more oddity: a stall of 0 isn't "no wait". It's correct but costs about 33 cycles, which is why code compiled with -O0 looks so slow.

How long everything takes

With a trustworthy runner (it checks the disassembly of the timed loop before spending any GPU time), the rest was patient measurement. Memory latency spans more than an order of magnitude:

A ceiling that turned out to be the compiler's fault

Ampere is supposed to run 32-bit float and integer instructions side by side. In my measurements a mix of float FMAs and integer shifts never got close, and for a while I believed the hardware just couldn't. It turned out to be the register file. It has two banks, each able to serve one read per cycle, and an FMA reads three registers. ptxas had put the FMA's operands in the same bank.

What I took from Part I: the documented model of the GPU is missing rules that decide performance, and you can find them by breaking things on purpose.
Part II

Beating the compiler, once

Most of the time ptxas is right. I found one thing it doesn't model.

Memory reaches the SM in 32-byte sectors. In some quantized matrix-vector kernels, ptxas schedules two loads that each need half of the same sector far apart, and by the time the second one runs the sector has to be fetched again. So I wrote 3080lab optimize. It reads the load addresses in the SASS symbolically, finds these split pairs, moves the late half next to its partner, regenerates every control bit, checks for hazards, and compares the output bit for bit with the original.

One kernel isn't a result, so I froze the tool and ran it blind on 120 kernels it hadn't been built on:

suitekernelsspeedup (geomean)wrong outputs
A, used while building561.036×0
B, held out431.074×0

Then I got ambitious and wrote a full instruction scheduler using the same rules, hoping to beat ptxas everywhere. It reached parity, 1.003×, and stayed there. When I measured an oracle that picks the best of three orderings for every kernel, it only reached 1.005×. There wasn't much left to win. Along the way the hazard checker found a rule I'd missed (memory instructions need at least 4 cycles between issues), and a 1-cycle gap had quietly broken one test suite.

What I took from Part II: beating a mature compiler means finding the specific thing it doesn't model, not doing its general job better.
Part III

A real model, end to end

Did any of it add up to something you'd notice?

I took Qwen2.5-1.5B and loaded llama.cpp's own Q4_0 weight file, repacked bit-exactly so both engines read the same bytes. Then I wrote the engine around it: about 200 fused kernels captured in one CUDA graph, int4 matrix-vector kernels for one sequence, tensor-core kernels for batches, and int8 tensor-core prefill straight from the 4-bit weights. On day one it was already 1.28× llama.cpp. The current numbers, against the newest llama.cpp, in paired rounds with an identical-binary control:

At one sequence, a token takes 1.95 ms and spends 63% of the card's peak bandwidth reading 928 MB of weights; most of the gain over llama.cpp comes from fewer, fused launches. The bigger gains with several sequences come from reading each weight once for all of them on tensor cores. Outputs match a token-by-token reference, and perplexity is within 0.1% of an fp16 path.

A detour that didn't payI also built a decode "megakernel": one persistent kernel for the whole step, a producer warp streaming weights through shared memory and consumer warps doing the math. It compiled cleanly, ran without timeouts, picked the wrong token, and was slower than the CUDA graph anyway.
Part IV

Model, or just search?

If you can try every option, why model the hardware at all?

By November I had a runtime model with single-digit median error, and the question I kept coming back to was whether it's actually useful for decisions. I wrote down the test, the split and what counts as a win before fitting anything, then measured 771 decisions:

decisionbest fixed rulemodeloracle
launch structure (fusion, CUDA graphs)1.159×1.229×1.231×
reordering SASS instructions1.000×1.0007×1.005×

Choosing how to launch work, the model is within 0.2% of perfect. Reordering instructions, even perfect knowledge only buys 0.5%.

Against autotuning

Autotuning just times candidates and keeps the fastest. In small spaces (4 to 21 candidates) the model was no better than a rule of thumb plus a couple of measurements. The interesting case was the prefill GEMM, which has 212 valid tile shapes. On four layers of Llama-3-8B, a model the cost model had never seen, I timed every tile and checked every output:

Running as I write this. Four layers isn't enough to believe in. The proper test is on the GPU now: 32 workloads from Qwen2.5-7B, Gemma-2-9B, Phi-3-mini and Qwen2.5-14B at two prompt lengths, all 212 tiles each, checked against an fp32 reference, and the model racing Optuna's TPE autotuner from 0 to 64 measurements. The bar, written down before the first timing: reach within 5% of the best with 4× fewer measurements than TPE. The result goes here whichever way it lands.
What I took from Part IV: a hardware model earns its keep when the space is too big to search, not when it's small enough to just try everything.
Part V

What didn't work

This list is longer than the list of wins. I think it's the most honest part of the project.

  • A general SASS scheduler. Parity with ptxas, never better. Joint register allocation plus scheduling, and software pipelining, didn't help either.
  • Letting the model decide when to rewrite. No better than always rewriting, and only 5 of 9 right calls under register pressure.
  • The decode megakernel. Wrong token, slower than the graph.
  • Ranking close GEMM tiles. In blind tests the model got single trends right (occupancy 15 of 16), but picking between two good tiles was close to a coin flip (0.57).
  • A correctness check that couldn't fail. My test activations weren't validly quantized, so every output was NaN and the comparison meant nothing. I caught it, rebuilt the check around the production quantizer, and every tile passed.
  • Selling the 3090. See the prologue.
Epilogue

Trying not to fool myself

A GPU is a noisy instrument, and it's easy to see a 2% win that isn't there. The habits that stuck:

Measure the noise first. Time two identical binaries against each other. Anything smaller than that gap isn't a result. Interleave everything. Never run all of A, then all of B; heat and clocks drift. Write the rule down before the number exists, and if it has to change, say when and why. Check outputs, not just times, because a fast wrong kernel is the easiest win to believe.

All of this is one RTX 3080. None of the hardware rules have been checked on another card, and the SASS rewrites are tested, not proven equivalent (the verification notes list the gaps). The code, the raw data and the day-by-day notebook are all on GitHub.
